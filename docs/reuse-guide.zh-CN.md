# 垂类复用指南

[English](reuse-guide.md) · [中文](reuse-guide.zh-CN.md)

本指南用于把 YuStream/LitStream 适配到另一个垂类：课程、招聘、商品、活动、新闻、媒体、内部文档，或任何目录型场景——只要其中每个物品都有一段文本描述。

关于复用，实话实说：

- 如果你的物品能用现有字段（`title`、`abstract`/描述、`authors`/品牌、`fields`/标签、`summary`）表示，适配工作主要就是 **提示词 + 入库 + 文案**。
- 如果你的物品需要不同字段，你还需要改动后端的**物品 schema**、你的入库管线以及前端。
- 你**不**需要训练排序模型，也不需要构建特征管线。
- 你**不**需要使用 `searcher/`。它只是一个 arXiv 参考生产器；你的入库路径可以是任何能产出物品契约的东西。

## 1. 哪些属于框架层，哪些属于领域层

| 层 | 框架层 | 领域层（新垂类需要改动） |
| --- | --- | --- |
| 推荐闭环 | 缓存/粗排/精排/反馈 | 哪些交互重要、更新节奏 |
| 检索 | Embedding + Milvus + top-K + 最近过滤 | 嵌入模型、物品文本、top-K |
| 精排 | 强制工具调用、从 1 开始的索引、outline | 提示词、多样性目标、物品数量 |
| 画像 | `summary` + `interest_topics` 拆分 | 画像维度、信息需求模型 |
| 目录 | MySQL `items` + Milvus `(id, vec)` | 字段、来源、去重键、富化提示词 |
| 入库 | `raw → semantic text → vector → (MySQL + Milvus, same id)` 契约 | 来源、工具、映射、富化 |
| UI | 推荐流、卡片、详情、引导 | 文案、卡片布局、交互事件 |

保留 **画像 → 主题 → 嵌入 → 召回 → 精排 → 交互 → 画像** 的闭环。改变的是其中的内容和判断标准。

### 案例扩展与框架优化

本指南讲的是**案例扩展**：在现有闭环上交付一个新的垂类。如果你想改变闭环本身——检索、精排器、画像引擎、服务、成本或多租户——请阅读[扩展与优化](extending.zh-CN.md)。两者可以同时做，但除非你是有意迁移，否则应保持那份文档中的契约稳定。

## 2. 七步适配

### 第 1 步 — 定义物品与用于嵌入的文本

用一段话写清楚：用户是在哪些东西之间做选择，以及什么文本最能代表一个物品。然后选择**一个**用于嵌入的文本字段。

示例：

| 垂类 | 物品 | 嵌入文本（示例） |
| --- | --- | --- |
| 论文 | arXiv 论文 | 问题 + 方法 + 结果概述 |
| 课程 | 课程 | 难度 + 教学大纲 + 技能 + 形式 |
| 招聘 | 职位 | 角色 + 职责 + 技术栈 + 资历 |
| 商品 | SKU | 品类 + 使用场景 + 材料 + 差异点 |
| 活动 | 活动 | 主题 + 受众 + 形式 + 讲者 |
| 内部文档 | 文档 | 目的 + 决策 + 涉及的系统 |

同一段文本也应当展示给精排器（或它的精简衍生版本）。在 LitStream 中，`items.summary` 既是用于嵌入的文档，也是精排器的输入。

### 第 2 步 — 构建入库适配器（或复用参考实现）

`searcher/` 是**可选的**。它是针对 arXiv 的一套完整参考实现；可以把它当作模板，也可以用任何语言自己写加载器。值得借鉴的是**流程**，而不一定是实现：原始物品信息 → 语义文本 → 向量 → 对应的写入。

不变式是：

```text
raw item information → item semantic text → embedding vector
                                   │
                    MySQL `items` row + Milvus `(id, vec)` with the same id
```

规则：

1. **选择你的来源和工具。** 官方 API、爬虫、CMS 导出、CSV、队列或内部定时任务都可以。
2. **映射字段**到后端读取的 `items` 各列。保留一个稳定的去重键。LitStream 使用 `items.url`；商品用 SKU，招聘用申请 ID，课程用课程代码。如果 `url` 不稳定，就新增一个专用标识列，并更新去重查询。
3. **生成语义文本**并存入 `items.summary`（或你选定的字段）。如果这一步用了 LLM，请让输出保持为**纯文本**，因为它会被直接嵌入。
4. **先写 MySQL**，拿到物品 ID，再向 Milvus 写 `(id, vec)`。务必让 MySQL 与 Milvus 使用同一个 ID，不要让两个 ID 出现分叉。
5. **先去重再富化**，这样就不会为已入库的物品重复支付 LLM/翻译调用费用。
6. **先验证再全量导入**：用小批量核对行数/向量数、做一次抽样向量检索，并抽样调用一次 `GET /api/items/recommend`。

如果你保留参考 searcher，请把 `searcher/arxiv/` 换成你的来源客户端，并重写 `ingest/mapping.go`；它流程的其余部分依然适用。

### 第 3 步 — 选择嵌入模型与维度

- 后端（用于 `interest_topics`）和入库管线（用于物品文本）要使用同一个模型。参考 searcher 读取同一份 `.env` 正是为此。
- 把 `VEC_DIM` 设为模型的输出维度。示例中使用 1024。
- 每个垂类使用独立的 Milvus collection。不要把不同模型的向量混在一起。
- 如果之后要更换模型，请新建 collection、重新嵌入全部数据，然后再切换 `MILVUS_COLLECTION_NAME`。

### 第 4 步 — 重写提示词

提示词集合位于 [`backend/llm/prompt.go`](../backend/llm/prompt.go)，另有一条在 [`searcher/llm/summary.go`](../searcher/llm/summary.go)：

| 提示词 | 保持不变的部分 | 需要按领域重写的部分 |
| --- | --- | --- |
| `PromptGenerateUS` | 输出 `summary` + `interest_topics`；topics 就是召回查询 | 什么算好画像；哪些需求可预测 |
| `PromptUpdateUS` | 使用新的/历史的交互；保持 topics 格式稳定 | 哪些行为代表兴趣；兴趣衰减有多快 |
| `PromptUpdateWithNewInfo` | 除非字段变化很大，否则只做最小改动 | 哪些字段是有意义的 |
| `PromptRecommend` | 只选择给定的索引；返回 `outline`；允许多样性 | “好”的含义；多样性维度；风险/覆盖度 |
| 参考 searcher 的摘要提示词（可选） | 纯文本、不臆造、300–500 tokens | 由“问题/方法/结果”改为“角色/技能/匹配度”等 |

#### 画像提示词清单

- 把画像定义为**长期 + 推断出的信息需求**，而不是一串关键词。
- 把 `interest_topics` 定义为**短期、具体、可变化**的。它会被嵌入；一整段散文是不好的召回查询。
- 要求模型在多次更新之间保持 topic 格式稳定（例如始终是 "topic: subtopic" 这样的行），这样向量之间仍然可比。
- 如果有帮助，加入“确定需求 vs 不确定需求”的划分，供精排器使用。
- 明确 JSON/工具 schema，并禁止输出多余文本。

#### 精排提示词清单

- 给模型一个明确目标：满足推断出的信息需求，而不是最大化相似度。
- 要求多样性（方法、来源、价格带、资历、主题）。
- 禁止使用外部知识和虚构物品。
- 说明从 1 开始的索引契约，以及确切的输出字段名。
- 候选格式保持简洁：`index. summary`。
- 决定给模型看画像 summary、topics，还是两者都给。LitStream 两者都给；topics 锚定召回，summary 提供意图。

#### 可复用的精排模板

```text
你是面向 <垂类> 的推荐决策引擎。
给定用户画像、当前兴趣主题，以及一个带编号的候选列表，
精确选出 <N> 个最能满足用户信息需求的物品。
在 <维度> 上优先保证多样性；不要选择近似重复的物品。
只使用给定的候选。不要编造事实。
以 JSON 返回：
- items_list: 从 1 开始的候选索引，长度为 <N>
- outline: 一段描述本窗口的文字
```

### 第 5 步 — 适配交互与 UI

| LitStream 事件 | 通用含义 | 垂类示例 |
| --- | --- | --- |
| `click` | 打开详情 / 跳出 | 打开职位、加入购物车、查看教学大纲 |
| `scroll` | 在某个窗口内停留 | 同上 |
| `like` | 收藏/喜欢 | 加入候选清单、书签 |
| `view` | 详情页停留 | 阅读时长、视频观看时长 |

需要改动：

- 如果新增交互类型，改 `backend/domain/models_domain.go`（`InteractionType`）。
- 改 `backend/llm/prompt.go`，说明每种类型的含义。
- 改 `frontend/src/api/interactions.js` 来上报该事件。
- 改 `frontend/src/components/*` 来采集它（按钮、计时器、滚动深度）。

如果某个信号噪声较大（例如误点击），请在提示词中给它加权，或在发送前先聚合。后端存储原始事件；解释发生在提示词里。

### 第 6 步 — 调优检索与精排

| 调节项 | 影响 | 起始值 |
| --- | --- | --- |
| `SEARCH_TOP_K` | 召回广度与提示词 token 量 | 50–100 |
| `LIMIT_TOP_K` | 窗口大小与用户的选择负担 | 10–20 |
| `RECS_WINDOW` | 防重复轮数 | 5–10 |
| `RECOMMEND_TTL` | 精排后的窗口可复用多久 | 15–30 分钟 |
| 更新节奏 | 画像新鲜度 vs LLM 成本 | 每个 3–5 个 LLM 窗口 |
| 摘要长度 | 嵌入质量 vs 提示词成本 | 200–500 tokens |

小目录（物品少于 10k）可以调低 `SEARCH_TOP_K`；大目录可以提高，但要关注提示词大小。如果精排器经常返回少于 `LIMIT_TOP_K` 个物品，请检查提示词的索引契约和候选数量。

### 第 7 步 — 先评估再宣称质量

至少要做到：

- **离线：** 构建 30–100 个带标注的用例（画像/查询 → 相关物品）。衡量粗排阶段的 recall@K，以及精排窗口的 precision/NDCG。在相同候选集上比较提示词版本。
- **线上：** 点击率、点赞率、滚动深度/停留时长、窗口间留存、多样性，以及“不感兴趣”（如果你加了）。
- **成本：** 每个窗口的 token 数、每个会话的 LLM 调用数、每次画像更新的嵌入调用数。
- **失败：** 空窗口、工具调用格式错误、索引越界、画像更新失败。

不要在候选集不同的情况下比较提示词改动；请保持召回固定。

## 3. 版本迁移

### 仅改提示词

现状：提示词是 Go 常量。流程是：

1. 编辑 `backend/llm/prompt.go`。
2. 重新构建/重启后端（`docker compose up -d --build backend` 或 `go run ./cmd`）。
3. 重跑一个固定的离线评估集。
4. 如果你有路由能力，先对一个实例或一个用户群做金丝雀发布。

目前没有提示词注册表。如果需要 A/B 测试，请增加 `PROMPT_VERSION` 环境变量并在启动时选择一套提示词，或者把提示词外置到表/文件中。

### 更换嵌入模型或维度

这是一次数据迁移，而不是改配置：

1. 用新的 `VEC_DIM` 创建新 collection。
2. 重新嵌入每个物品（完整重新入库后执行 `regen-embedding`，或运行专门的迁移任务）。
3. 让所有 `vec:user:*` 缓存失效。
4. 切换 `MILVUS_COLLECTION_NAME` / `VEC_DIM`。
5. 保留旧 collection 直到新 collection 通过评估，然后再删除。

绝不要把旧模型和新模型的向量写入同一个 collection。

### 物品 schema 变更

需要同时修改：

- `backend/domain/models_domain.go`（GORM + JSON 字段）
- `searcher/domain/item.go`（必须保持列兼容）
- `searcher/ingest/mapping.go`
- `frontend/src/utils/format.js` 以及卡片/详情组件
- 引用这些字段的提示词

然后执行 MySQL 迁移（AutoMigrate 会新增列，但不会转换数据）并回填。

### 更换 LLM 提供方

后端的 endpoint 硬编码为 DeepSeek；searcher 的摘要 endpoint 硬编码为 Qwen MaaS。若要使用其他提供方：

1. 在 `backend/pkg/llm.go`（以及 `searcher/llm/client.go`）中增加 base URL + 鉴权头的配置。
2. 确认该提供方支持强制工具调用，否则改用严格的 JSON 输出。
3. 重新测试解析、截断和索引越界。
4. 重跑离线评估；模型变化会改变排序行为。

## 4. 多垂类或多租户

当前部署是单垂类的：

- 一个 `MILVUS_COLLECTION_NAME`
- 一套提示词
- 一张 `items` 表

若要支持多个垂类，最小设计是：

| 关注点 | 改动 |
| --- | --- |
| 向量 | 每个垂类一个 collection（`<vertical>_items`） |
| 提示词 | 按垂类/租户选择提示词集 |
| 物品 | 增加 `vertical_id` 列 + 带作用域的查询 |
| 画像 | 每个垂类一份用户画像，或一份全局画像加垂类兴趣 |
| 路由 | 从 host/path/tenant 解析垂类，然后选择 collection + 提示词 |
| 缓存 | 每个 Redis key 都包含垂类 |

这些尚未实现。不要以为现有 key 具备租户隔离。

## 5. 成本控制

闭环成本主要来自：

1. **精排调用：** 每次 LLM 响应一次。降低 `SEARCH_TOP_K`、缩短摘要、提高缓存 TTL，或对低流量用户跳过精排。
2. **画像更新：** 每 5 个 LLM 响应一次。加大间隔，或对交互做防抖。
3. **入库：** 每个新物品一次摘要 + 一次翻译。富化前先去重已经实现；不要盲目回填。
4. **嵌入：** 每个物品一次、每次画像变更一次。缓存向量（已实现），并避免不必要的画像重写。

先上便宜的杠杆：更短的摘要、更低的 top-K、每个会话更少的窗口，以及在低峰期批量入库。

## 6. 法律与合规

- 遵守来源方的条款、robots 政策和速率限制。arXiv 有 API 使用规范；商业目录可能需要授权。
- 只存你需要的数据。画像和交互流可能包含个人数据。
- 告知用户 LLM 会处理其画像和交互，并链接隐私政策。
- 提供删除/导出途径。MySQL 行是持久化的；Redis TTL 不是删除策略。
- 未经领域评审和人工监督，不要将系统用于受监管的决策（信贷、就业、住房、医疗）。
- 检查 LLM/嵌入提供方的数据保留和跨境传输条款。

## 7. 适配清单

- [ ] 已选定入库路径；`searcher/` 是可选的，物品契约明确。
- [ ] 已定义物品 schema 与嵌入文本。
- [ ] 已实现来源适配器和去重键。
- [ ] 入库管线与后端使用相同的嵌入模型/维度。
- [ ] 已用小批量完成入库并验证（行数/向量数、抽样检索、抽样推荐流）。
- [ ] 画像提示词定义了长期需求 + 短期主题。
- [ ] 精排提示词强制索引、多样性和 outline。
- [ ] 交互含义有文档记录，并由 UI 上报。
- [ ] `SEARCH_TOP_K` / `LIMIT_TOP_K` / `RECS_WINDOW` / TTL 已调优。
- [ ] 已有离线评估用例，提示词改动在固定候选上比较。
- [ ] 已测试失败路径：LLM 超时、空 collection、Redis 丢失、画像缺失。
- [ ] 已完成隐私/法务评审。

## 8. 反模式

- **把 `searcher/` 当作必需项。** 它只是一个参考生产器；任何写入物品契约的管线都可以。
- **拿很长的画像摘要去做嵌入。** 召回会变噪；应改为嵌入短 topics。
- **让 LLM 编造物品 ID。** 始终把索引映射回给定候选，并做边界检查。
- **跳过粗排兜底。** 每个请求都等 LLM 会毁掉推荐流体验。
- **多个嵌入模型共用一个 collection。** 距离会失去意义。
- **把 `RECS_WINDOW` 当作物品数量。** 它是轮数；要乘以 `LIMIT_TOP_K` 才能估算被排除的物品数。
- **每个事件后都更新画像。** 成本高且抖动；应批量或防抖。
- **只优化相似度。** 提示词应要求多样性和信息需求匹配。
- **没有评估就宣称质量。** 闭环看起来合理；未经测量就不算被证明。

如果你要改动闭环本身而不是新增垂类，请见[扩展与优化](extending.zh-CN.md)。
